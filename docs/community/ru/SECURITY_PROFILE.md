# Production-профиль безопасности

*In English: [SECURITY_PROFILE.md](../en/SECURITY_PROFILE.md)*

`NXS_ANOMALY_PROFILE=production` переводит все связанные с безопасностью значения
по умолчанию в безопасное состояние одним переключателем, чтобы защищённая
инсталляция не зависела от того, вспомнили ли вы про дюжину отдельных флагов.
**Каждое значение ниже по-прежнему переопределяется** своей переменной окружения —
явное значение всегда сильнее профиля, так что от любого пункта можно отказаться.

| Настройка | По умолчанию (без профиля) | В production | Переопределение |
|---|---|---|---|
| SSRF-гейт (блокировка приватных/loopback/link-local адресов доставки) | выкл | **вкл** | `NXS_ANOMALY_BLOCK_PRIVATE_WEBHOOKS` |
| Лимит приёма webhook (токенов/с на ключ интеграции, **на под**) | выкл (0) | **50** | `NXS_ANOMALY_WEBHOOK_RATE` |
| Лимит API (токенов/с на IP клиента, **на под**) | выкл (0) | **20** | `NXS_ANOMALY_API_RATE` |
| Circuit breaker доставки (подряд идущих отказов на канал/цель) | выкл (0) | **5** | `NXS_ANOMALY_CIRCUIT_BREAKER_THRESHOLD` |
| Новые inline-секреты в запросах создания/изменения | разрешены | **отклоняются** (нужен `env:ПЕРЕМЕННАЯ`) | — (только профиль) |

Политики `NXS_ANOMALY_BLOCKED_CHANNELS` и `NXS_ANOMALY_EGRESS_ALLOWLIST` не
получают неявных значений даже в production: допустимые мессенджеры и внешние
домены — организационное решение, которое приложение не может угадать.

Cookie сессии и без профиля выставляются с флагом `Secure`
(`NXS_ANOMALY_SESSION_COOKIE_SECURE`), а управляющий API и без профиля отклоняет
неаутентифицированные запросы, пока его не откроют явно — профиль ничего из этого
не ослабляет.

## Что закрывает SSRF-гейт

URL, который сервис пойдёт запрашивать, выбирает любой, кто может править цепочку
эскалации или цель уведомления. Поэтому при включённом гейте проверка обязана
пережить недобросовестного получателя. Она выполняется **в HTTP-транспорте**, а не
только над URL из конфигурации, и именно это делает верным следующее:

| Попытка | Результат |
|---|---|
| URL, указывающий прямо на приватный/loopback/link-local адрес | отклоняется до запроса |
| Разрешённый хост отвечает `302` на `169.254.169.254` или внутренний сервис | отклоняется в момент соединения — проверяется каждый переход |
| Имя резолвится в публичный адрес при проверке и в приватный при соединении (DNS rebinding) | отклоняется — соединение идёт на уже проверенный адрес, второго резолва между ними нет |
| Имя отвечает публичным **и** приватным адресом одновременно | отклоняется целиком, а не «берём публичный» |
| Редирект на не-HTTP схему | отклоняется |

Редиректы между разрешёнными хостами по-прежнему выполняются, до обычного лимита
в 10 переходов — провайдеры, отвечающие `302`, продолжают работать.

С выключенным гейтом (умолчание вне production-профиля) ничего из перечисленного
не действует, и доставка на локальный адрес работает как раньше — на это
рассчитаны среды разработки.

### Исключения для внутренних получателей

Получатель внутри вашей же сети — чат-шлюз в том же кластере, внутренний
трекер — имеет приватный адрес по определению, и гейт его отвергает. Вместо того
чтобы выключать гейт целиком (production-профиль в Helm-чарте этого не позволяет),
назовите такой адрес в `NXS_ANOMALY_BLOCK_PRIVATE_WEBHOOKS_EXCEPT`:

```bash
NXS_ANOMALY_BLOCK_PRIVATE_WEBHOOKS_EXCEPT=gw.chat.svc.cluster.local,.corp.example,10.20.0.0/16
```

Записи через запятую, в синтаксисе `NXS_ANOMALY_EGRESS_ALLOWLIST`:

| Запись | Что совпадает |
|---|---|
| `gw.chat.svc.cluster.local` | это имя хоста — как оно написано в URL или в редиректе |
| `.corp.example` | `corp.example` и все поддомены (но не `evilcorp.example`) |
| `10.20.0.0/16`, `10.96.14.7` | адрес, к которому реально идёт соединение |

Предпочитайте имя хоста: оно исключает одного получателя, а CIDR на всю сеть
сервисов открывает её целиком для любого, кто может править цепочку. Исключение
снимает запрет только с **приватных** диапазонов (RFC 1918 и `fc00::/7`).
Loopback, link-local (к нему относится cloud metadata `169.254.169.254`) и
unspecified-адрес отвергаются при любом списке. Остальное не меняется: адрес
по-прежнему проверяется при соединении и на каждом редиректе. С выключенным гейтом
список ничего не делает, о чём сервис предупреждает при старте.

### Гейт и прокси доставки

Если для канала задан прокси (`NXS_ANOMALY_DELIVERY_PROXY_*`, см.
[PROXY.md](PROXY.md)), картина
для этого канала меняется, и это стоит решить осознанно:

- **адрес самого прокси разрешён всегда**, даже приватный: egress-прокси на
  `10.x` — обычная схема, и именно оператор его назвал;
- **адрес назначения проверяется настолько, насколько его видит сервис** — его
  резолвит и набирает прокси, поэтому проверки на соединении нет. Заранее
  отвергаются IP-литерал из приватного, loopback или link-local диапазона и имя,
  которое локально резолвится в такой адрес; имя без локального ответа
  пропускается (в сети с намеренно испорченным DNS это обычный случай), а имя,
  которое во внутренний адрес превращает только DNS прокси, сервису не видно.
  Редирект на такой IP-литерал тоже отвергается;
- **что продолжает действовать** — `NXS_ANOMALY_EGRESS_ALLOWLIST`, по написанному
  URL и на каждом редиректе, а также запрет не-HTTP схем;
- **каналы без прокси** (включая попавшие в `NXS_ANOMALY_DELIVERY_NO_PROXY`)
  проверяются полностью, как описано выше.

Практический вывод: проксировать имеет смысл каналы с фиксированным адресом
провайдера (telegram, slack, mattermost, mobile). Для канала `webhook`, где URL
задаёт редактор цепочки, прокси стоит включать только вместе с
`NXS_ANOMALY_EGRESS_ALLOWLIST`.

## Политика каналов и исходящего трафика

`NXS_ANOMALY_BLOCKED_CHANNELS=telegram,slack,mattermost` запрещает канал и при
сохранении конфигурации, и непосредственно перед доставкой. Вторая проверка
нужна для старых записей, созданных до включения политики.

`NXS_ANOMALY_EGRESS_ALLOWLIST` принимает через запятую точные hostname,
hostname с ведущей точкой (домен и его поддомены) и CIDR. Если список задан,
каждый исходящий HTTP destination и каждый редирект должны ему соответствовать;
SSRF-проверка приватных адресов продолжает действовать независимо. Отказы имеют
явные причины `channel_blocked_by_policy` и `destination_not_allowlisted` и не
маскируются как успешная доставка.

## Персональные данные

Production readiness предупреждает, пока не выбраны сроки хранения аудита,
уведомлений, delivery attempts и web-сессий. Это предупреждение, а не
автоматическая политика: юридически значимые сроки задаёт оператор. Процедуры
экспорта/erase и перечень копий вне PostgreSQL описаны в
[DATA_INVENTORY.md](DATA_INVENTORY.md).

## Лимиты и число реплик

Лимитеры считают по-разному, и разница становится важной при масштабировании API.

| Лимитер | Где живут корзины | Область действия заданной величины |
|---|---|---|
| Приём webhook (`NXS_ANOMALY_WEBHOOK_RATE`) | в процессе API | **на под** |
| Управляющий API (`NXS_ANOMALY_API_RATE`) | в процессе API | **на под** |
| Попытки входа (не настраивается) | PostgreSQL | **на весь кластер** |

Первые два стоят на горячем пути, где обращение в базу на каждый принятый алерт
стоило бы дороже, чем даёт защита; они существуют, чтобы один процесс не захлебнулся,
а не чтобы держать общекластерную квоту. Поэтому при `api.replicaCount: 4` и
`NXS_ANOMALY_WEBHOOK_RATE=50` инсталляция целиком принимает 200/с.

Chart принимает ту величину, которая вам действительно нужна, и делит её сам:

```yaml
api:
  replicaCount: 4
rateLimits:
  webhookRatePerCluster: 100   # отрендерится как NXS_ANOMALY_WEBHOOK_RATE=25
  apiRatePerCluster: 40        # отрендерится как NXS_ANOMALY_API_RATE=10
```

Заданный напрямую `NXS_ANOMALY_WEBHOOK_RATE` (через `config`/`extraConfig`)
по-прежнему работает и передаётся как есть — это величина на под.

Лимитер входа устроен иначе намеренно. Лимит на под для попыток пароля означает,
что атакующий, распределяющий перебор по подам, получает N-кратное число попыток:
лимит, которому глобальность нужнее всего, масштабировался бы вместе с
инсталляцией. Его корзины живут в `nxs_anomaly_rate_buckets` (миграция 0024), а сам
лимит — пять попыток, дальше одна в десять секунд, на IP клиента — действует на все
реплики сразу. Списываются только **неудачные** попытки: успешный вход возвращает
свой токен обратно, поэтому общий выходной IP не запирает собственных пользователей.

Если PostgreSQL недоступен, лимитер входа **пропускает** запрос, а не отклоняет его.
Это осознанно: путь входа всё равно нуждается в базе, чтобы вообще проверить пароль,
поэтому отказ «на всякий случай» превратил бы сбой базы в полную недоступность входа,
ничего при этом не защитив. Событие пишется в журнал как `rate_limiter_unavailable`.

## Ссылки на секреты (`env:ПЕРЕМЕННАЯ`)

Секреты отдельных объектов, хранящиеся в базе — `webhook_secret` интеграции,
`webhook_url` ChatOps-канала, `headers` ChatOps-канала и шага `TRIGGER_WEBHOOK`,
`push_token` мобильного устройства — можно задавать
ссылкой вместо литерала:

```json
{ "name": "acme", "webhook_secret": "env:NXS_ANOMALY_ACME_HMAC" }
```

В момент использования значение берётся из названной переменной окружения, так что
секрет в открытом виде никогда не лежит в PostgreSQL. В production-профиле **новый**
inline-секрет (не ссылка) отклоняется с понятной ошибкой; уже лежащие в базе legacy-
значения продолжают работать, поэтому обновление версии не ломает инсталляцию —
переводить их на ссылки можно в своём темпе.

## Как убедиться, что профиль включён

И API, и worker пишут свою фактическую конфигурацию безопасности в журнал при
старте. Быстрая проверка, что гейт работает:

```bash
# с профилем доставка на loopback-webhook отклоняется (SSRF-гейт)
NXS_ANOMALY_PROFILE=production nxs-anomaly serve ...
```

Поведение покрыто регрессионным набором тестов безопасности
(`internal/{utils,engine,server}/*security*_test.go`, `*profile*_test.go`), который
идёт в CI как `test:security`.
