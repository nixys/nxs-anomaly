# Универсальный JSON webhook

## Подготовка установки

Нужны работающие API и воркер nxs-anomaly, права редактора, тестовый получатель и доступ к настройкам отправителя. Из сети отправителя проверьте публичный HTTPS-адрес и сертификат. [Установка nxs-anomaly](INSTALLATION.md).

## Подключение отправителя

1. В nxs-anomaly создайте цепочку с уведомлением тестового пользователя. В разделе «Интеграции» создайте тестовую интеграцию типа `webhook`, назначьте цепочку по умолчанию и скопируйте ключ.
2. Настройте отправитель так, чтобы он передавал заголовок, состояние и метки сервиса в полях JSON из примера. Сохраняйте `dedupe_key` на время инцидента, а для каждого нового события задавайте отдельный nxs_event_id. Пример рассчитан на тестовую интеграцию без webhook_secret. Для подписанных запросов настройте общий секрет и заголовки подписи по справочнику API.
3. В тестовой оболочке задайте API с базовым адресом установки и KEY с ключом интеграции. Выполните запрос ниже из сети отправителя.

```bash
curl --fail-with-body -i -X POST "$API/integrations/v1/webhook/$KEY" \
  -H 'Content-Type: application/json' \
  --data-binary '{"title":"API latency","status":"firing","dedupe_key":"checkout-test","nxs_event_id":"checkout-test-01","labels":{"service":"checkout"}}'
```

## Проверка жизненного цикла

Повторите запрос с тем же ID события и проверьте ответ duplicate. Для закрытия отправьте status resolved с новым ID события и прежним dedupe_key. В истории группы проверьте выполнение выбранной цепочки и сопоставьте попытку доставки с уведомлением у адресата.

После подтверждения доставки закройте тестовый инцидент соответствующим событием восстановления.

```bash
curl --fail-with-body -X POST "$API/integrations/v1/webhook/$KEY" \
  -H 'Content-Type: application/json' \
  --data-binary '{"title":"API latency","status":"resolved","dedupe_key":"checkout-test","nxs_event_id":"checkout-test-02","labels":{"service":"checkout"}}'
```

## Эксплуатация и диагностика

При неверной группировке или отсутствии доставки сравните поля и метки события с предпросмотром маршрута. При 404 проверьте полный путь и действующий ключ. При 503 учитывайте Retry-After. После ротации ключа сразу обновите отправитель и повторите тест. [Маршруты и уведомления](CONFIGURATION.md) · [Преобразование полей](ALERT_PROCESSING.md) · [Ответы HTTP](API.md).
