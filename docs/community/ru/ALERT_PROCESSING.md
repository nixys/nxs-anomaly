# Обработка алерта: разбор, обогащение, шаблоны, удаление данных

*In English: [ALERT_PROCESSING.md](../en/ALERT_PROCESSING.md)*

Что происходит с алертом от момента, когда его приняли на webhook, до текста,
который читает разбуженный человек, — и где на этом пути данные добавляются, а
где удаляются.

Это справочник по одному сквозному пути. Как создать интеграцию, маршрут и
цепочку — в [CONFIGURATION.md](CONFIGURATION.md); что представляет собой каждая
сущность — в [DOMAIN_MODEL.md](DOMAIN_MODEL.md); какие данные где лежат и
сколько живут — в [DATA_INVENTORY.md](DATA_INVENTORY.md).

## 1. Порядок стадий

```
HTTP-запрос на /integrations/v1/<source>/{key}
        │
        ▼
1. Разбор источника   normalize*Alert() — привести формат источника к общему виду
        │
        ▼
2. Выбор маршрута     selectRoute() — по лейблам ИСХОДНОГО алерта
        │
        ▼
3. Пайплайн           extract / set / rename / remove / gsub / truncate / drop
        │             (обогащение и удаление данных; drop прекращает обработку)
        ▼
4. Нормализация полей title, severity, status, dedupe_key
        │
        ▼
5. Группировка        поиск активной AlertGroup по (integration_id, dedupe_key)
        │
        ▼
6. Эскалация и доставка   рендер шаблона уведомления на канал
```

Порядок стадий 2 и 3 неслучаен и разобран в §4: **маршрут выбирается до
пайплайна**, всё остальное видит уже обогащённый алерт.

Реализация: `internal/engine/ingest.go`, `ingest_sources.go`, `routing.go`,
`pipeline.go`, `notifications.go`, `engine_helpers.go`.

## 2. Разбор: приведение источника к общему виду

Каждый эндпоинт приёма имеет свой нормализатор, который переводит формат
источника в единый внутренний алерт. Дальше по конвейеру источник уже неотличим:
пайплайн, маршрут, группировка и шаблоны работают с одними и теми же полями.

| Эндпоинт | Нормализатор | Значение `source` |
|---|---|---|
| `POST /integrations/v1/webhook/{key}` | нет (формат уже целевой) | `webhook` или `source_type` интеграции |
| `POST /integrations/v1/alertmanager/{key}` | `normalizeAlertmanagerAlert` | `alertmanager` |
| `POST /integrations/v1/pagerduty/{key}` | `normalizePagerDutyAlert` | `pagerduty` |
| `POST /integrations/v1/victorops/{key}` | `normalizeVictorOpsAlert` | `victorops` |
| `POST /integrations/v1/grafana-alerting/{key}` | `normalizeGrafanaAlertingAlert` | `grafana_alerting` |
| `POST /v2/alert/pool` | `IngestLegacyPool` | `nxs-alert-compat` |

### 2.1. Общий вид алерта после разбора

Поля, которые понимает всё, что ниже по потоку:

| Поле | Смысл | Если не пришло |
|---|---|---|
| `title` | заголовок | `title` → `labels.alertname` → `labels.summary` → `Incoming alert` |
| `message` | тело | пусто |
| `status` | `firing` / `resolved` | `status` → `labels.status` → `firing` |
| `severity` | важность | `severity` → `labels.severity` → `unknown` |
| `labels` | плоская карта `string → string` | `{}` |
| `annotations` | плоская карта, в маршрутизации не участвует | `{}` |
| `dedupe_key` | ключ группировки | вычисляется, см. §3 |
| `fingerprint` | отпечаток источника | пусто |
| `starts_at`, `ends_at` | время по версии источника | `null` |
| `generator_url` | ссылка в источник | `null` |
| `notification_channels` | список каналов только для этого алерта | не задаётся |
| `emergency_alert` | аварийный алерт; включается и лейблом `emergency=true` | `false` |
| `payload` | исходное тело запроса целиком | — |

`status` из множества resolved-значений закрывает группу: приходит событие
восстановления, группа резолвится системным актором, а все её алерты
переводятся в `resolved`. Событие восстановления без открытой группы возвращает
`result: resolved_without_group` — это не ошибка.

### 2.2. Alertmanager (v4)

Конверт разбирается по алертам: каждый элемент `alerts[]` становится отдельным
алертом, но **все они принимаются одной транзакцией** под одной advisory-блокировкой
интеграции. Невалидный конверт не принимается целиком.

| Внутреннее поле | Откуда |
|---|---|
| `title` | `annotations.summary` → `annotations.description` → `labels.alertname` → `receiver` |
| `message` | `annotations.description` → `annotations.message` → `title` |
| `status` | `alert.status` → `envelope.status` → `labels.status` → `firing` |
| `severity` | `labels.severity` → `envelope.status` → `unknown` |
| `dedupe_key` | `fingerprint` → `groupKey` → `alertmanager_group:<groupLabels>` |
| `starts_at` / `ends_at` / `generator_url` | `startsAt` / `endsAt` / `generatorURL` |

Конверт целиком (receiver, groupLabels, commonLabels, commonAnnotations,
externalURL, truncatedAlerts) сохраняется в `payload.alertmanager`.

### 2.3. PagerDuty Events v2

| Внутреннее поле | Откуда |
|---|---|
| `title` / `message` | `payload.summary` → `client` |
| `status` | `resolved`, если `event_action = resolve`, иначе `firing` |
| `severity` | `payload.severity`, но всё вне `critical`/`warning`/`info` становится `warning` |
| `labels` | `payload.custom_details` целиком + `component`, `group`, `class`; `payload.source` → лейбл `host` |
| `dedupe_key`, `fingerprint` | `dedup_key` |

### 2.4. VictorOps / Splunk On-Call

| Внутреннее поле | Откуда |
|---|---|
| `title` | `entity_display_name` → `entity_id` |
| `message` | `state_message` |
| `status` | `resolved`, если `message_type = RECOVERY` |
| `severity` | `CRITICAL`/`PROBLEM` → `critical`, `WARNING` → `warning`, `INFO` → `info`, остальное → `warning` |
| `labels` | `host_name` → `host`, `monitoring_tool`, `service`, **плюс все остальные строковые поля тела** кроме служебных |
| `dedupe_key`, `fingerprint` | `entity_id` |
| `starts_at` | `state_start_time` (Unix-секунды) → ISO |

`message_type: ACKNOWLEDGEMENT` обрабатывается отдельно и алерта не создаёт.

### 2.5. Grafana Alerting (webhook v2)

Как Alertmanager, с двумя отличиями: `status` становится `resolved` также при
`envelope.state = ok`, а `title` дополнительно смотрит в `envelope.title`.
Специфика Grafana (`ruleUrl`, `dashboardURL`, `panelURL`, `silenceURL`,
`values`, `valueString`, `orgId`) сохраняется в `payload.grafana_alerting`.

### 2.6. Legacy-пул NXS (`/v2/alert/pool`)

Совместимость с `nxs-alert`. Обязательны `triggerMessage` и `monitoringURL`.
`title` — первая строка `triggerMessage`, обрезанная до 160 рун. Severity —
`critical` при `isEmergencyAlert: true`, иначе `warning`. `alertChannel`
разбирается в список каналов; если в нём нет ни `telegram`, ни `call`,
добавляются оба, и всегда добавляется `email`.

## 3. Ключ дедупликации

Группировка идёт по паре (`integration_id`, `dedupe_key`) среди
нерезолвленных групп. Ключ берётся из первого доступного:

1. `dedupe_key`, если его прислал источник (или подставил нормализатор:
   `fingerprint`, `dedup_key`, `entity_id`, `groupKey`);
2. иначе — по полю интеграции `group_by`: `k1=v1|k2=v2` из перечисленных
   лейблов, которые фактически есть на алерте;
3. иначе — `title=<заголовок>`.

Отсюда практическое следствие: **пайплайн влияет на группировку**. Вырезанный из
заголовка build id склеивает ночную серию падений в один инцидент; добавленный
лейбл, попавший в `group_by`, наоборот разносит алерты по разным группам.

## 4. Пайплайн: обогащение и удаление данных

Поле `pipeline` интеграции — список этапов, который переписывает алерт после
выбора маршрута и до всего остального.

### 4.1. Почему маршрут выше пайплайна

Обогащение правят часто и разные люди: лейбл `team` для дашборда, `namespace`,
вытащенный из заголовка. Если бы это влияло на выбор маршрута, каждая такая
правка меняла бы то, кого поднимут ночью, руками человека, который про эскалацию
не думал. Поэтому маршрут следует из алерта в том виде, в каком его прислал
источник, и чтение маршрутов интеграции даёт полную картину, куда уходят её
алерты.

Всё ниже по потоку видит уже обогащённый алерт: ключ дедупликации и, значит,
группировка; сохранённый алерт и его лейблы; текст уведомления и UI.

Единственное, чего порядок не позволяет: правилом перенаправить алерт на другую
цепочку эскалации. В этом и смысл.

### 4.2. Этапы

Каждый этап — **одно действие** и необязательное условие `if`. Два действия в
одном этапе отклоняются при сохранении интеграции: порядок между ними не был бы
виден в конфиге, а порядок здесь и есть вся семантика.

| Действие | Форма | Что делает |
|---|---|---|
| `extract` | `{"from": "<поле>", "pattern": "…(?P<имя>…)"}` | вытаскивает именованные группы регулярки в лейблы |
| `set` | `{"<лейбл>": "<значение>", …}` | добавляет или перезаписывает лейблы |
| `rename` | `{"<старое>": "<новое>", …}` | переименовывает лейбл |
| `remove` | `["<лейбл>", …]` | **удаляет лейблы** |
| `gsub` | `{"field": "<поле>", "pattern": "…", "replace": "…"}` | переписывает поле регуляркой |
| `truncate` | `{"field": "<поле>", "max": N}` | ограничивает длину поля (N — байты, рез на границе руны) |
| `drop` | `true` | **отбрасывает алерт целиком** |

Адресуемые поля: `title`, `message`, `severity` и `label:<имя>`. Больше ничего:
этап не дотягивается до сырого `payload` и не может создать структуру, которой
остальной приём не ожидает.

Условие `if` — ровно одна проверка: `equals`, `matches` или `exists`.

```json
{
  "pipeline": [
    { "extract": { "from": "title", "pattern": "pod (?P<pod>\\S+) in (?P<namespace>\\S+)" } },
    { "if": { "field": "label:namespace", "matches": "^pay" }, "set": { "team": "payments" } },
    { "remove": ["__name__", "prometheus_replica", "customer_email"] },
    { "gsub": { "field": "title", "pattern": "\\s+run-[0-9a-f]+$", "replace": "" } },
    { "truncate": { "field": "message", "max": 2000 } },
    { "if": { "field": "label:severity", "equals": "info" }, "drop": true }
  ]
}
```

### 4.3. Правила, которые стоит знать заранее

- **`extract` не перезаписывает то, что прислал источник.** Он добавляет
  контекст; чтобы именно заменить лейбл, поставьте после него `set` — так замена
  читается как замена.
- **`drop` без `if` отклоняется.** Безусловный сброс молча выключает интеграцию:
  она продолжает отвечать `202`, но не будит никого. Сброшенный алерт возвращает
  `result: dropped_by_pipeline` — это `202`, а не ошибка: отправитель доставил
  алерт, получатель по конфигу решил не действовать.
- **Ошибка этапа не роняет алерт.** Этап пропускается, в лог идёт
  `alert_pipeline_stage_skipped` с номером этапа. Недоставленный алерт хуже
  необогащённого: первое — пропущенный инцидент, второе — косметика.
- **Пустое значение не затирает поле.** Обратно в алерт `title`, `message` и
  `severity` пишутся, только если пайплайн оставил их непустыми.
- **Некорректное правило отклоняется при сохранении интеграции** (`400`), а не
  при первом боевом алерте.
- **Лимиты:** до 32 этапов, регулярка до 512 символов, поле длиннее 16 КБ не
  обрабатывается (этап пропускается), до 32 именованных групп в одном `extract`.
  Регулярки Go — это RE2, катастрофического бэктрекинга нет, поэтому лимиты про
  латентность на горячем пути приёма, а не про ReDoS.
- **Кэш компиляции.** Скомпилированный пайплайн кэшируется по отпечатку самого
  определения, поэтому правка применяется без рестарта, а неизменённая
  интеграция стоит одного поиска в карте на алерт.

### 4.4. Проверка правила до боевого алерта

`POST /api/v1/routes/debug/{key}` прогоняет пайплайн так же, как приём, и
возвращает блок `pipeline`:

| Поле ответа | Что показывает |
|---|---|
| `labels_before` / `labels_after` | лейблы до и после пайплайна |
| `labels_added` | чего не было у источника |
| `labels_changed` | `{"<лейбл>": {"from": …, "to": …}}` |
| `labels_removed` | что удалено |
| `title_before` / `title_after` | заголовок до и после |

Маршрут в ответе считается по исходным лейблам — ровно как при приёме, поэтому
предпросмотр показывает то, что произойдёт с боевым алертом.

## 5. Шаблоны уведомлений

### 5.1. Где задаются

`templates` интеграции — объект `{"<канал>": "<шаблон>"}`. Ключ `default`
применяется, если для канала своего шаблона нет. Пустое значение или отсутствие
ключа — рендерится встроенный формат (§5.2).

```bash
api -X PUT "$API/api/v1/integrations/{id}" -d '{
  "templates": {
    "default": "[{{ .severity }}] {{ .title }}\n{{ .reason }}\nГруппа: {{ .group_id }}",
    "telegram": "🔥 {{ .title }}\npod={{ .label_pod }} ns={{ .label_namespace }}\n{{ .reason }}"
  }
}'
```

**Какие каналы читают шаблон.** Сегодня — только `telegram` и `email`; каждый
берёт ключ со своим именем, а если его нет — `default`. Остальные каналы шаблон
игнорируют, и это надо учитывать, задавая `default`:

| Канал | Текст сообщения |
|---|---|
| `telegram` | `templates.telegram` → `templates.default` → встроенный формат |
| `email` | `templates.email` → `templates.default` → встроенный формат |
| `slack`, `mattermost` | всегда встроенный формат |
| `chatops` | всегда встроенный формат |
| `log` | всегда встроенный формат (строка лога `notification_log_delivery`) |
| `webhook` | не текст: уходит JSON в форме Alertmanager |
| `call` | фраза для синтеза: `Alert. <title>. See messages for details.` (`Emergency alert.` при `critical`) |
| `mobile` | push-нагрузка, шаблон не применяется |
| `issue` | свои `subject_template` / `body_template` на шаге цепочки, см. §5.6 |

Шаблоны кэшируются в процессе на время TTL референс-кэша (равен интервалу опроса
воркера). Правка через API сбрасывает кэш в том поде, который её обслужил;
остальные реплики подхватят её по истечении TTL — не мгновенно, но и не до
рестарта.

### 5.2. Встроенный формат (когда шаблона нет)

```
[<severity>] <title>
<reason>
<лейблы, кроме alertname и severity, в виде k=v, k=v>
Alert group: <group_id>
```

Строка лейблов сортируется (один и тот же алерт всегда читается одинаково) и
обрезается на 400 символах с многоточием: у Telegram и SMS есть свои лимиты, а
алерт Alertmanager может нести десятки лейблов.

### 5.3. Переменные

| Переменная | Значение |
|---|---|
| `title` | заголовок алерта (по умолчанию `Alert notification`) |
| `severity` | важность (по умолчанию `unknown`) |
| `reason` | причина уведомления: шаг эскалации, `alert resolved` и т.п. |
| `group_id` | ID группы алертов |
| `status` | статус группы (по умолчанию `open`) |
| `labels` | все лейблы одной строкой `k=v, k=v` |
| `label_<имя>` | значение одного лейбла |
| `user_name`, `user_username` | получатель уведомления |

`label_<имя>`: имя приводится к нижнему регистру, всё вне `[a-z0-9_]` становится
подчёркиванием — `kubernetes.io/name` доступен как `{{ .label_kubernetes_io_name }}`.
Обращение вида `{{ .labels.pod }}` **не работает**: контекст перед рендером
превращается в плоскую карту строк, поэтому у лейбла есть только плоский ключ.
Если лейбл называется так, что его ключ совпадает со встроенной переменной,
побеждает встроенная.

### 5.4. Синтаксис

Движок — `text/template`. Поддерживаются формы `{{ .title }}`, `{{ title }}`,
`{{title}}` (легаси-плейсхолдеры переписываются в точечную форму) и
CamelCase-алиасы: `{{ .Title }}`, `{{ .Severity }}`, `{{ .GroupID }}`,
`{{ .UserName }}` — так их пишут примеры Terraform-провайдера. Доступны обычные
конструкции: `{{ if .severity }}…{{ else }}…{{ end }}`, `{{ range }}`, `{{ with }}`.

Значения подставляются буквально: текст, похожий на плейсхолдер, внутри
заголовка алерта повторно не разворачивается.

### 5.5. Что происходит при ошибке в шаблоне

Доставка не срывается. Шаблон рендерится запасным путём — простой заменой
известных плейсхолдеров, — и неизвестный плейсхолдер остаётся в тексте как есть.
В лог пишется `notification_template_parse_failed` (синтаксическая ошибка) или
`notification_template_render_failed` (неизвестный ключ; в этой же записи
перечислены поддерживаемые). Второе логируется один раз на шаблон, а не на
каждое уведомление.

### 5.6. Шаблоны шага `CREATE_ISSUE`

У шага эскалации `CREATE_ISSUE` свои два шаблона, задаются на шаге цепочки, а не
на интеграции:

| Поле | Значение по умолчанию |
|---|---|
| `subject_template` | `[{{ severity }}] {{ title }}` |
| `body_template` | `Alert group: {{ group_id }}\n\nTitle: {{ title }}\nSeverity: {{ severity }}` |

Контекст здесь у́же: `title`, `severity`, `group_id`, `status`, `labels`.
Переменных получателя нет — у задачи в трекере нет адресата.

## 6. Удаление данных

Удаление живёт на трёх разных уровнях, и путать их не надо: первый решает, что
вообще попадёт в базу, второй — что увидит читающий, третий — сколько это
хранится.

### 6.1. При приёме — пайплайн

Единственное место, где данные можно **не сохранять вовсе**.

- `remove` — выкинуть лейблы до записи. Так убирают технический мусор
  (`__name__`, `prometheus_replica`) и, что важнее, значения, которых в системе
  оповещения быть не должно: адреса и телефоны клиентов, попавшие в лейблы
  мониторинга.
- `gsub` — вырезать или замаскировать фрагмент внутри `title`, `message` или
  лейбла, когда целиком поле нужно.
- `truncate` — ограничить длину поля.
- `drop` — не сохранять алерт целиком.

Ограничение, о котором стоит знать: пайплайн работает с `title`, `message`,
`severity` и лейблами. **Исходное тело запроса сохраняется в `payload` алерта
как есть** и пайплайном не правится. Если удалить надо именно оттуда — либо
источник не должен это присылать, либо горизонт хранения групп (§6.3) должен
быть настроен под это.

### 6.2. На чтении — редакция

Поля, похожие на учётные данные, маскируются на пути чтения API (`***` + четыре
последних символа): push-токен мобильного устройства и `webhook_url`
ChatOps-канала. Доставка читает те же строки через store и видит настоящие
значения — это осознанное разделение: путь доставки это код, путь чтения это
ответ человеку. `webhook_url` остаётся видимым тем, кто может править
конфигурацию, иначе форму настроек нельзя было бы сохранить, не затерев значение.

### 6.3. По сроку — retention

Свип идёт каждый цикл воркера, по категориям, независимо друг от друга. `0` —
хранить вечно; это же и дефолт для новых категорий, потому что обновление версии
не должно начинать удалять данные, которых никто не просил удалять.

| Категория | Переменная | Дефолт | Что удаляет |
|---|---|---|---|
| `alert_groups` | `NXS_ANOMALY_ALERT_GROUP_TTL_DAYS` | `30` | резолвленные группы и их алерты вместе с `payload` |
| `chatops_messages` | `NXS_ANOMALY_CHATOPS_MESSAGES_TTL_DAYS` | `30` | зеркало ChatOps-переписки |
| `audit_events` | `NXS_ANOMALY_AUDIT_RETENTION_DAYS` | `0` | аудит: актор, IP, действие |
| `notifications` | `NXS_ANOMALY_NOTIFICATION_RETENTION_DAYS` | `0` | кого, куда и когда разбудили |
| `delivery_attempts` | `NXS_ANOMALY_DELIVERY_ATTEMPT_RETENTION_DAYS` | `0` | попытки доставки: ответы провайдеров, тексты ошибок |
| `web_sessions` | `NXS_ANOMALY_WEB_SESSION_RETENTION_DAYS` | `0` | сессии браузера: IP и user-agent |

Удаление видно в логе (`retention_deleted`, уровень info) и в метрике
`nxs_anomaly_retention_deleted_total{category}`. Категория с заданным сроком и
плоским счётчиком — это свип, который перестал работать. Ошибка свипа пишется
уровнем error: данные, которые должны были уйти, всё ещё здесь.

Ручной аналог для двух категорий доступен через API — архивация резолвленных
групп и ChatOps-сообщений.

### 6.4. По запросу человека — экспорт и стирание

Отдельные административные операции над данными конкретного пользователя
(`export_personal_data`, `erase_personal_data`), обе аудируются — включая
стирание. Запись об удалении не называет ни одного персонального значения: ID,
актор, время и счётчики. Подробности и полный каталог того, что где лежит, — в
[DATA_INVENTORY.md](DATA_INVENTORY.md).

## 7. Наблюдаемость приёма

| Сигнал | О чём |
|---|---|
| `result` в ответе приёма | `ingested`, `resolved`, `resolved_without_group`, `dropped_by_pipeline` |
| `alert_pipeline_stage_skipped` | этап пайплайна не отработал; в записи номер этапа и интеграция |
| `alert_pipeline_ignored` | пайплайн интеграции не компилируется и целиком проигнорирован |
| `notification_template_parse_failed` | шаблон не разобрался, ушёл запасной рендер |
| `notification_template_render_failed` | неизвестный плейсхолдер; в записи список поддерживаемых |
| спан `ingest.alert` | трассировка приёма; через ID группы связывается с эскалацией и доставкой (см. [TRACING.md](TRACING.md)) |

Журнал группы (`logs`) фиксирует и стадию приёма: `group_created`,
`alert_attached`, `source_resolve`.
